# craft Review Rules

The rules craft's own reviewers apply to every PR. A rule marked **I** (Important)
is a requirement while implementing and a blocker in the Factory's code-review gate;
**N** (Nit) is advisory.

# Review instructions

This repo has several independently gated units: `compute-plane-python/`,
`control-plane/`, `customer-ui/`, `bundles/`, `tools/` and `e2e/`. Each has its
own stack. A pattern from one unit does not carry to another. Give separate
evidence for each unit a finding touches.

Each unit's review rules are in `.claude/skills/craft-review/units/<unit>.md`, with
`repo-wide.md` applying to every PR. Where a unit has CLAUDE.md files, they hold
the detail behind those rules. The rules are derived from past review findings,
the CLAUDE.md files and incidents, and each one cites its evidence.

The review dispatches read-only subagents (`.claude/agents/review-*`) for
independent lenses and merges what they find. They follow
`.claude/skills/craft-review/contract.md` and report in the severities below. Run it
locally with the `craft-review` skill (`/craft-review`) before asking for review.

## The standard

Judge a change by one test: does it leave code health better than before.
Code health, not perfection, is the bar. Do not block a change over a Nit
alone.

## Severity

Mark a finding Important only when it breaks behavior, leaks tenant data, or
blocks a rollback. Examples: wrong logic, a query with no tenant filter, a
secret in code or logs, a migration unsafe for the previous release, a change
to the pinned HTTP route table.

Treat any violation of a CLAUDE.md file (root or per-unit) as Important.

Mark style, naming, and refactor suggestions as Nit at most. Mark a defect
that predates this diff as Pre-existing — do not charge the author for it.

## What to check, beyond "does it compile"

- **Complexity.** Flag a solution bigger than the problem it solves. A
  general-purpose mechanism built for a one-off need is a defect, not a
  feature — this repo's own tiebreaker rule names this directly.
- **Tests.** Confirm a test exists for new behavior and that the test would
  fail if the behavior broke. A test that cannot fail checks nothing.
- **Consistency.** When a local pattern conflicts with general style, follow
  the local pattern, unless the PR's own goal is to change that pattern.
- **Every line.** Read lines the diff did not mark as changed too, not only
  the added ones. A changed context can break an unmarked line.

## Hunt for the bug the last review round missed

Do not repeat a finding an earlier round already raised and the author
resolved. Find a new bug instead.

Trace a change past the edited lines. Check the callers, the other modules
that share the touched state, and the tests that exercise the old behavior.
A bug that needs the whole diff to see is worth more than a bug visible in
one hunk.

Give a `file:line` reference for every finding. Do not guess a file name or
infer a bug from a symbol's name alone.

## Check the diff against the stated goal

Read the PR description before the diff. State whether the diff meets the
goal the description claims.

Flag a diff that does less than the description claims as Important.

Flag a diff that changes more than the goal needs as a Nit, and name the
extra files.

For a change on a request path (API route, UI flow, CLI command), trace one
call end to end: the caller, the handler, and the response the caller gets
back. Do not stop at the first function the diff touches.

## Keep nits useful

Report at most five Nits per review.

Do not report an issue CI already catches: lint, format, type checks, import
boundaries, or a per-unit gate script.

## Do not review

- Generated files, lockfiles (`pnpm-lock.yaml`, `uv.lock`, `Cargo.lock`), and
  build output (WASM, compiled assets).
- The historical shape of a merged migration file. Migrations are frozen
  after merge to `main`; review only the new file stacked on top.
- `decisions/`, `DECISIONS.md`, and files under `docs/superpowers/plans/`.
  These are append-only or scratch, not reviewed code.

## Verify a self-reported fix, do not trust the description

A PR description may name specific corrections it claims to have made
against a design spec or an earlier draft. Check each named correction
against the diff with a `file:line` citation. A claim the diff does not
back is itself a finding, at the severity the underlying defect would carry.

## Always close with a summary

State the finding count by severity. If there are none, write "No issues
found" in plain words.

## Severity (from .claude/skills/craft-review/contract.md)


Report in `REVIEW.md`'s three severities, which win over any scale a lens brief uses:

- `important`: breaks behaviour, leaks tenant data, blocks a rollback, breaks a pinned contract or
  another unit, or violates a `CLAUDE.md` / unit rule marked Important. A lens's `blocking` maps
  here; its `should_fix` maps here only if it meets this definition, otherwise to `nit`.
  A failure path that leaves committed data unreadable, half-granted or inconsistent for good — not
  just a worse error message — is `important`.
- `nit`: anything else worth saying. A lens's `observation` maps here.
- `pre_existing`: a defect the diff did not introduce. Never charge the author for it.

When unsure between `important` and `nit`, say why in the evidence and pick `nit`. The main
reviewer can raise it; a false Important blocks a PR.
