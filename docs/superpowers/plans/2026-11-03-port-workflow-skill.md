# Port-workflow Skill Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `port-workflow` skill to the EM-AISoftwareFactory, plus the harness and config changes to run it, so that a single command ports one em-semi Prefect workflow into craft with parity tests, evals and a gap report.

**Architecture:** The skill is a markdown procedure (`skills/port-workflow/SKILL.md`) with reference docs and templates that encode the analog-trim porting model. The harness gains a generic "run this skill prompt" path in `Executor.execute_with_provenance` and a `port` CLI command that targets the newly registered `craft` repo. The existing `implement` path keeps its exact prompt and behaviour.

**Tech Stack:** Python 3 harness (argparse, PyYAML), pytest (new, dev-only), Claude Code plugin skills (markdown + YAML frontmatter), bash.

**Spec:** `docs/superpowers/specs/2026-11-03-port-workflow-skill-design.md`

## Global Constraints

- Scope is the Factory update only. Do not run the five real ports. The only runs are the two acceptance runs in Task 7, and nothing from them is merged.
- `python -m harness implement` must keep building exactly `/autonomous-implement {issue_key} --context-file {ctx} --provenance-file {events}[ --branch {branch}]`.
- The skill is fully autonomous: no confirmation questions (same banner as `integrate-prototype`).
- `--jira-key` is required for both the skill and `python -m harness port`. Commit and PR titles in craft start with `[Jira:KEY]`. The skill never adds the `nojira` label.
- em-semi is read-only. Read it through `git show <ref>:<path>`, never a checkout. Copy from a pinned sha recorded in the vendor script.
- Vendored files are changed only by sed import rewrites in the vendor script and by numbered patches under `patches/`. No hand edits.
- No fresh rewrites of analysis code, including large orchestration modules (vendor them as-is, replace only the Prefect orchestration).
- Fixture data is em-semi's synthetic/demo test data. Never real customer lots.
- The skill writes only inside its target bundle and shared Pack-level stand-ins. Runner-image, SDK and plane changes go in the gap report.
- Parity is checked in two layers: static tests (vendored em-semi tests as the oracle, plus goldens generated from craft's nodes, analog-trim style) and evals. LLM steps call the real model via `llm.complete`; no record/replay.
- PRs are never auto-merged.

## Review Focus

- Unknown workflow name: the skill must stop before creating a branch, emit `run_complete` with `outcome: failed`, and name the specs it searched. (Task 6, structural test)
- em-semi tests already failing at the pinned ref: record them in the gap report as pre-existing and finish `partial`. Never make them pass by editing vendored code. (Task 6)
- Re-running on a workflow whose bundle already exists: re-vendor through the script, keep existing patches, never wipe hand-written `nodes/` or stand-ins silently. (Task 6)
- `python -m harness port` without `--jira-key`: argparse error, no Claude launch. (Task 2 test)
- em-semi checkout missing or the ref doesn't resolve: the vendor script exits non-zero with a clear message before writing anything. (Task 5 test)
